# 6.3 增强：案例研读固定信源 [进阶]

> 来源：[ACM Queue](https://queue.acm.org/) · [Latent Space](https://www.latent.space/) · [InfoQ 中文](https://www.infoq.cn/)

## 概念：为什么需要

**业务痛点**：架构师断层——能设计系统的人稀缺 [已必备]；而架构判断力主要靠「见过足够多真实系统」积累。场景实例：方案评审在立项前拦住一个坑——评审者的判断力来自对真实案例的拆解积累，而不是天赋。

- **从哪来**：道听途说的架构故事（二手转述，失真）→ 技术博客（质量参差）→ 固定信源（一手叙事，可追溯）
- **是什么**：三个固定信源，每季度各挑 1 篇做拆解：
  - **ACM Queue**：资深工程师一手架构叙事，深且慢
  - **Latent Space**：AI 工程实践访谈，工程视角而非学术
  - **InfoQ 中文**（infoq.cn）：架构 / AI 落地中文一手报道
- **往哪去**：拆解产出沉淀为「案例库」（问题 → 约束 → 决策 → 教训），配合 6.1 ADR 形成「决策 → 复盘」闭环；正好匹配 6.3「每季度更新」的节奏

**引导反思**：决策质量靠「见过足够多真实系统」——案例研读是架构师最便宜的「实战经验」。

## 动手

拆解四步法（每季度从三个源各挑 1 篇，共 3 篇）：

1. **问题**：这篇案例要解决什么业务 / 技术问题？规模与约束是什么？
2. **约束**：团队、时间、成本、合规等限制条件——脱离约束谈决策没有意义
3. **决策**：关键决策是什么？备选方案被否掉的理由是什么？
4. **教训**：哪些经验可迁移到自己的系统？哪些是特定场景不可迁移的？

产出格式建议：每篇拆解写成 1 页 markdown，存 `docs/part6-architect/cases/`（或自己的笔记库），标注原文链接与阅读日期。

## 实用技巧

- 固定信源 + 固定节奏：每季度 3 篇（每源 1 篇），比「刷到啥看啥」积累更快
- 拆解时先写「约束」再写「决策」——脱离约束的决策评价都是事后诸葛亮
- 只引用可打开的原文（官方博客、RFC、事故报告），二手转述不进案例库
- 案例库与 6.1 ADR 联动：自己写 ADR 时，翻案例库找「类似决策别人怎么做的」
- 中文信源（InfoQ）用于快速了解，事实与数据回英文原文复核（检索手册 §0 纪律）

## 考察问题

- 为什么案例研读要「固定信源」而不是「全网搜」？（线索：一手叙事可追溯；二手转述失真；信源质量决定案例库质量）
- 拆解时「约束」为什么比「决策」更重要？（线索：同样的决策在不同约束下结论可能相反）
- 怎么判断一篇案例的教训能不能迁移到自己的系统？（线索：对比约束条件——规模、团队、业务形态）

## 经验之谈

- 观点（不署名）：案例研读的价值在「决策质量」的积累——读 100 篇二手转述不如拆 10 篇一手叙事（通行工程共识，具体引用待补）
- Gergely Orosz（The Pragmatic Engineer）：以真实工程决策复盘见长——「决策是怎么做出的、代价是什么」正是案例研读要拆的东西（信源介绍，见检索手册 §10）
- Latent Space（swyx & Alessio）：AI 工程实践访谈——AI 系统的真实约束与取舍，工程视角而非学术（信源介绍，见检索手册 §10）

## 架构师视角

- 解决什么问题：用一手案例训练「决策质量」——见过足够多真实系统的取舍，评审时才能拦住坑
- 何时用：阶段三持续学习；每季度固定节奏，配合 6.1 ADR 与 6.4 持续学习
- 何时不用：阶段一 / 二先别花时间——没有实操基础，案例拆解只是看故事
- 权衡：每季度 3 篇的投入换案例库积累；拆解质量 > 数量
- 固定三问：
  - 平台提供了什么能力边界？——研读案例时对照自家平台：案例里的方案，自家平台支持吗（API / CRD / 控制台）？
  - 业务接入点在哪？——案例的「决策」落到自家系统时，接入点是什么、迁移点在哪
  - 需要和基础设施团队对齐什么？——案例涉及平台能力（如 GPU 调度、网关）时，把问题清单带给平台方

## 常见问题排查

| 问题 | 排查路径 |
|---|---|
| 拆解写成「文章摘要」 | 检查是否回答了「约束 → 决策」——没有约束分析的拆解只是复述 |
| 案例库积灰没人看 | 与 6.1 ADR 联动：写 ADR 时先查案例库；季度复盘时过一遍 |
| 信源打不开 / 链接失效 | 只引用可打开的原文；失效链接从案例库移除，标注日期 |
