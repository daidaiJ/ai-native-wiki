# 6.1 增强：ADR 架构决策记录模板 [进阶]

> 来源：[adr.github.io](https://adr.github.io/) · 验证环境：待验证

## 概念：为什么需要

**业务痛点**：技术决策失误代价高——一次错误选型可能等于两年重构 [已必备]。更隐蔽的是「决策失忆」：半年后没人说得清某个方案是深思熟虑还是拍脑袋，重构时不敢动、评审时无据可依。场景实例：一次错误选型导致的重构复盘——复盘时发现当初的选型理由早已散落在会议纪要里，无人回看。

- **从哪来**：口头决策 → 会议纪要（散落各处，没人回看）→ ADR（Architecture Decision Record，架构决策记录——一页纸记录一个决策的「为什么」，对抗「当初为什么这么选」的失忆）
- **是什么**：一页纸记录一个决策的「为什么」：背景、决策、备选方案、后果、复核触发条件。不写长篇论证，只写结论与理由
- **往哪去**：ADR 进 Git 仓库随代码评审走——决策记录与代码同版本、可追溯、可回滚；配合 6.3 案例研读，形成「决策 → 复盘」闭环

6.1 主线（需求分析 → 技术选型 → 架构设计 → 方案文档模板）中，本增强聚焦方案文档里的 ADR 模板——方案文档建议直接内嵌 3~5 篇 ADR，比长篇论证更可维护。

**引导反思**：架构师的价值在「决策质量」不在「代码量」——ADR 让决策质量可评审、可追溯、可复盘。

## 动手（验证环境：待验证）

模板可直接复制进方案文档：

```markdown
# ADR-001：向量库采用 pgvector

- 状态：已接受（2026-08-28）
- 背景：RAG 需要向量检索；当前数据量 < 500 万条；团队已运维 PostgreSQL 集群
- 决策：首期用 pgvector，不引入专用向量库
- 备选方案：Qdrant（部署简单但新增组件）/ Milvus（分布式能力暂用不上）
- 后果：延迟换运维 simplicity；若向量超过千万级需迁移（迁移点：重建索引，见防腐层设计）
- 复核触发条件：向量规模 > 1000 万 或 QPS > 500
```

使用步骤：

1. 在方案文档仓库建 `docs/adr/` 目录，模板存为 `ADR-001.md`
2. 每做一个关键决策（选型 / 架构取舍 / 接口约定）写一篇，编号递增
3. 随方案文档一起提交评审，评审通过后状态改为「已接受」

（配套的向量库实操见 Part 2.3 前置小节「Embedding 与向量库选型」）

## 实用技巧

- 一个决策一篇 ADR，编号递增（ADR-001、ADR-002…）；状态机：提议 → 已接受 → 已废弃——废弃也要留档，写清为什么推翻
- 备选方案至少写 2 个，并写清「为什么不选」——这是评审时被问得最多的地方
- 复核触发条件必须可量化（规模 > X / QPS > Y），否则半年后没人知道什么时候该重审
- 拿不准的决策先写「提议」状态，评审通过再改「已接受」——ADR 也是评审的输入物
- 与代码同仓库存放（如 `docs/adr/`），随 PR 评审，避免决策记录与代码分家

## 考察问题

- 为什么 ADR 要写「备选方案」而不是只写决策本身？（线索：决策质量体现在「排除过什么」；评审者需要对照）
- 什么情况下 ADR 会变成「文档债」？（线索：决策已稳定、无人复核、与代码脱节——想想 Git 里多久没动过的文件）
- 复核触发条件触发后，正确的动作是什么？（线索：不是直接改决策，而是重新走一遍「背景 → 备选 → 决策」）

## 经验之谈

- 观点（不署名）：ADR 的价值不在模板格式，而在「决策可追溯」——半年后有人问「为什么用 pgvector」，答案在仓库里，不在某人的记忆里（通行工程共识，具体引用待补）
- Martin Fowler《Who Needs an Architect?》（2003，观点转述）：架构关乎「重要的事」——而什么算重要、为什么重要，正是 ADR 要回答的问题

## 架构师视角

- 解决什么问题：决策失忆与决策无据——把「为什么」从口头与会议纪要中解放出来
- 何时用：选型、架构取舍、接口约定等任何「影响半年后」的决策；方案文档内嵌 3~5 篇
- 何时不用：日常实现细节（改个字段名）、一次性决定——ADR 是给「重要的事」用的
- 权衡：每篇 ADR 有维护成本（状态更新、复核），用「复核触发条件」控制数量与生命周期
- 固定三问：
  - 平台提供了什么能力边界？——平台已有能力（向量库、网关、消息队列等）是 ADR「备选方案」的候选池：先查平台有什么，再决定要不要引入新组件
  - 业务接入点在哪？——决策落地为 API / CRD / 控制台操作时，ADR 的「后果」要写明接入方式与迁移点
  - 需要和基础设施团队对齐什么？——涉及平台能力（新组件引入、配额、网络策略）的决策，ADR 评审时同步给平台方

## 核心收获表

| 能力维度 | 具体收获 |
|---|---|
| 决策记录 | 能写出一页纸 ADR：背景 / 决策 / 备选方案 / 后果 / 复核触发条件 |
| 方案文档 | 方案文档内嵌 3~5 篇 ADR，评审者五分钟进入状态 |
| 决策演进 | 用复核触发条件管理决策生命周期，废弃决策留档可查 |

## 常见问题排查

| 问题 | 排查路径 |
|---|---|
| ADR 写成了「需求文档」 | 检查是否回答了「为什么选 A 不选 B」——没有备选方案对比就不是 ADR |
| 决策记录与代码脱节 | 把 ADR 放进代码仓库随 PR 评审，状态变更也走 PR |
| 复核条件触发但没人响应 | 把复核条件写进方案文档的「风险登记」，随 6.3 季度案例研读一起过 |
