# 6.2 增强：SLO 起步模板（SLI → SLO → 错误预算）[进阶]

> 来源：[Google SRE Book（免费全文）](https://sre.google/books/) · [DORA](https://dora.dev/) · 验证环境：待验证

## 概念：为什么需要

**业务痛点**：系统不可靠导致事故与信任崩塌 [已必备]——但「可靠」没有量化定义时就是各说各话：业务说「系统要稳」，开发说「已经 99% 了」，运维说「监控一切正常」。场景实例：SLO 事故复盘——错误预算烧完冻结发布，把「可靠性」从口号变成可执行的纪律。

- **从哪来**：无指标监控（一切正常但事故不断）→ 拍脑袋可用性目标（「我们要 99.9%」但说不清怎么算）→ SLO 体系（Google SRE 提出：SLI → SLO → 错误预算闭环）
- **是什么**：
  - **SLI**（Service Level Indicator，服务水平指标）：`好事件数 / 总事件数`。例：成功响应数 / 总请求数
  - **SLO**（Service Level Objective，服务水平目标）：给 SLI 定目标。例：99.9%
  - **错误预算**（error budget）：1 − SLO。99.9% = 每月允许 43.2 分钟不可用（30 天 × 24h × 0.1%）
- **往哪去**：SLO 与可观测体系打通（指标从 Prometheus / OTel 来，呼应 Part 1.8 / 4.2）；错误预算接发布流程，成为「可靠性治理」的日常机制

**预算纪律**：预算烧完 → 冻结新功能发布，只修稳定性——这一条是 SLO 体系真正起作用的机制：它把「可靠性」从口号变成有预算约束的工程决策。

6.2 主线还覆盖容灾 / 容量规划 / 故障演练，本增强聚焦 SLO 起步三步——这是可靠性设计的度量基础。

**引导反思**：可靠性是设计出来的，不是监控出来的——SLO 让「可靠」可度量、可预算、可决策。

## 动手（验证环境：待验证）

起步三步：

1. **先挑 1 个用户可感知的 SLI**（不要一上来 20 个指标）——例：请求成功率 = 成功响应数 / 总请求数
2. **定一个「敢公布」的 SLO**——例：99.9%（每月允许 43.2 分钟不可用）
3. **每月复盘错误预算消耗**——预算烧完冻结新功能发布，只修稳定性

SLI 指标示例（PromQL，验证环境：待验证）：

```promql
# 请求成功率 SLI：好事件（2xx/3xx）÷ 总请求
sum(rate(http_requests_total{status=~"2..|3.."}[5m]))
/
sum(rate(http_requests_total[5m]))
```

## 实用技巧

- 从 1 个 SLI 起步：用户可感知优先（成功率 / 延迟），不要一上来建 20 个指标的体系
- SLO 要「敢公布」：定一个业务能接受、团队能守住的数；先松后紧，别第一版就 99.99%
- 错误预算按月度滚动计算：99.9% = 每月 43.2 分钟，复盘时看「这个月还剩多少预算」
- 预算烧完的处置要提前约定：冻结新功能发布、只修稳定性——写进团队约定而不是临时拍板
- 指标口径与 Part 1.8 / 4.2 的可观测体系打通：SLI 指标从 Prometheus / OTel 来，别另起炉灶

## 考察问题

- 为什么「可用性 99.9%」这种拍脑袋目标不算 SLO？（线索：没有 SLI 定义「好事件」是什么，目标就无法度量）
- 错误预算烧完了，为什么是「冻结新功能」而不是「加班修」？（线索：预算机制的目的是让可靠性决策可预期，而不是靠突击）
- 一个 SLI 都没有的系统，怎么开始？（线索：从用户可感知的请求成功率 / 延迟起步，先有 1 个再谈体系）

## 经验之谈

- 观点（不署名）：SLO 的价值不在数字本身，而在「预算纪律」——预算烧完冻结发布，这一条让可靠性从口号变成可执行的约束（通行工程共识，具体引用待补）
- Google SRE Book 第 4 章（观点转述）：监控只有服务于 SLO 才有意义——没有 SLO 的监控只是「仪表盘装饰」

## 架构师视角

- 解决什么问题：把「可靠」从口号变成可度量、有预算约束的工程决策
- 何时用：有用户可感知的服务、有发布节奏、团队愿意为可靠性设预算
- 何时不用：内部一次性任务、无用户 SLA 的后台作业——先别上 SLO 体系
- 权衡：SLO 需要指标埋点与月度复盘投入；从 1 个 SLI 起步，别一上来建 20 个指标的体系
- 固定三问：
  - 平台提供了什么能力边界？——平台是否提供指标采集与告警（Prometheus / 平台监控），SLI 指标从哪来、保留多久
  - 业务接入点在哪？——SLI 埋点（业务代码 / 网关层）、错误预算看板、发布门禁
  - 需要和基础设施团队对齐什么？——指标口径、告警通道、发布流程里错误预算门禁的接入方式

## 常见问题排查

| 问题 | 排查路径 |
|---|---|
| 指标口径对不上（成功率 99.99% 但用户觉得卡） | 检查 SLI 是否只算了「成功」没算「慢」——延迟类 SLI 要定义「多慢算坏」 |
| 错误预算总在月底爆掉 | 复盘发布节奏与容量：预算消耗集中在发布后 / 大促，先看是不是容量问题 |
| 定了 SLO 但没人看 | 把错误预算接进发布门禁与告警——没人看的 SLO 只是文档 |
