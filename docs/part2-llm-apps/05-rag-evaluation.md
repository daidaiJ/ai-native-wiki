# 2.5 增强：RAG 质量评估——RAGAS 四指标 + CI 回归 [实用]

> 来源：[RAGAS 文档](https://docs.ragas.com/) · [promptfoo](https://www.promptfoo.dev/docs/intro/)（路径待验证）· 验证环境：待验证

## 概念：为什么需要

**业务痛点**：RAG 应用上线后，改 prompt / 换模型全凭感觉——「感觉变好了」没有依据，上线后质量回归没人发现。原 2.5 覆盖了平台层（Langfuse/LangSmith 可观测），缺「质量层」：没有它，AI 应用的价值（成本/效率/体验改善）无法度量。

- **从哪来**：人工抽查 → 指标化评估（LLM-as-judge，用大模型当裁判给答案打分）→ CI 回归（评估进流水线，改代码必须跑分）
- **是什么**：一套「问题 + 标准答案 + 标准检索片段」的金标集 + 一组量化指标 + 一个能接进 CI 的跑分工具
- **往哪去**：评估集成为资产，随 badcase 持续回填；评估从「上线前检查」变成「日常开发流程」

## 指标四件套（RAGAS 事实标准）

| 指标 | 度量什么 | 一句话人话 |
|---|---|---|
| faithfulness（忠实度） | 答案是否只来自检索内容 | 模型有没有瞎编 |
| answer relevancy | 答案是否切题 | 答非所问吗 |
| context precision | 检索内容里有效信息的排位 | 找回来的东西排得靠前吗 |
| context recall | 应检回的内容覆盖度 | 该找的都找回来了吗 |

## 动手（待验证）

> 验证环境：待验证

1. 建金标集：20~50 条「问题 + 标准答案 + 标准检索片段」，覆盖典型业务问题与已知 badcase
2. 跑分：用 `ragas` 对金标集计算四指标（CLI 用法以官方文档为准）
3. 接 CI：用 promptfoo 把跑分红绿灯接进流水线——改 prompt 必须跑评估，低于阈值阻断合并

## 实用技巧

- 指标分开看：faithfulness 低 = 模型在瞎编（查 prompt 与检索内容）；context recall 低 = 该找的没找回来（查切块与 embedding）——先定位再动手
- 金标集是资产：每次线上 badcase 都回填进金标集，评估集越滚越准
- 阈值先宽松后收紧：起步阶段先「不劣化」再「达标」，避免被指标绑架
- LLM-as-judge 有偏差：裁判模型与业务模型同源时分数可能虚高，必要时换裁判模型交叉验证

## 考察问题

- 为什么评估集要人工标注，而不是让 LLM 自己生成？（线索：金标集是「标准答案」，标准答案不能由被考者出）
- faithfulness 和 context recall 同时低，先查哪一层？（线索：一个指向生成侧，一个指向检索侧）

## 架构师视角

- 解决什么问题：让 RAG 质量可度量、可回归、可验收
- 何时用：任何要上线的 RAG 项目；何时不用：一次性原型可先不建
- 权衡：评估集建设有成本，但「没有评估集的 RAG 项目 = 没有测试的服务，不允许上线」
- **平台提供了什么能力边界**：评估工具链（RAGAS/promptfoo）可自建；平台侧关注 Langfuse 等可观测接入
- **业务接入点在哪**：金标集与评估脚本是业务资产，接进 CI 流水线
- **需要和基础设施团队对齐什么**：CI 跑评估的算力/额度、评估结果是否进统一可观测平台

## 常见问题排查

| 现象 | 排查路径 |
|---|---|
| 分数虚高但线上体验差 | 检查金标集是否过小/过偏、裁判模型是否与业务模型同源 |
| faithfulness 低 | 查 prompt 是否诱导模型自由发挥、检索内容是否被截断 |
| context recall 低 | 查切块粒度、embedding 与领域匹配度、检索 top-k 是否太小 |
