# 2.7 LLM 应用安全 [实用]

> 来源：[OWASP Top 10 for LLM Applications](https://genai.owasp.org/) · [Simon Willison: Prompt injection 系列](https://simonwillison.net/tags/prompt-injection/) · 验证环境：待验证

## 概念：为什么需要

**业务痛点**：Agent 会读网页、调工具、带权限——风险从「模型说错话」升级为「模型被人指挥做坏事」（[已必备]：Agent 越权操作造成业务事故）。这一章给的是业务开发者的安全底线，不是安全专家课程。

- **从哪来**：传统应用安全（输入校验/权限控制）→ LLM 应用新增「模型本身不可信」维度 → 提示注入成为新攻击面
- **是什么**：LLM 应用安全 = 传统安全基线 + 模型层风险（提示注入、输出处理不当等）
- **往哪去**：把模型当不可信组件，安全边界放在工具权限与数据隔离层——类比浏览器与操作系统

## 威胁速览（对齐 OWASP LLM Top 10，条目顺序以官网为准）

提示注入、敏感信息泄露、供应链（第三方模型 / 插件 / MCP server 本身作恶）、输出处理不当（模型输出二跳成 XSS/命令注入）、过度代理（excessive agency：工具权限给太大）、系统提示泄露、向量与嵌入弱点、无限制消耗（被刷 token）。

## 最关键的一组概念：直接 vs 间接提示注入

（Simon Willison 提出的划分）

- 直接注入：用户在输入框里直接骗模型——危害有限（用户骗自己）
- 间接注入：攻击者把指令藏进网页 / 文档 / 邮件，等 RAG 检索或 Agent 浏览时喂给模型——**这才是 RAG/Agent 的新攻击面**：你的检索源是不可信输入

## 防御分层（务实版）

1. 别指望 prompt 防注入——「请忽略以上指令」挡不住变体；prompt 是提示，不是防线
2. 权限最小化：工具只读优先、白名单化、每个工具独立配额
3. 隔离执行：Agent 的工具在独立容器 / 独立 ServiceAccount 里跑（K8s 擅长的事，呼应 Part 3）
4. 高危动作人在环节：删除、外发、付款必须人工确认
5. 输出侧防御：结构化输出（JSON Schema 约束）+ 输出按上下文编码

## 动手（待验证）

> 验证环境：待验证

给一个工具调用 Agent 的工具集加约束：

1. 去掉写操作：工具白名单只保留只读接口
2. 加每分钟调用上限：每个工具独立配额，防被刷
3. 输出走 JSON Schema 校验：校验失败即拒绝，防输出二跳注入

## 实用技巧

- 系统提示里写「忽略以上指令」类话术不是防线，别把它当控制措施
- 日志与可观测数据里不要记录 prompt 原文与工具入参原文（缩小敏感信息泄露面）
- 对用户输入与检索内容做长度/格式限制，降低注入载荷的可用空间
- 上线前安全评审：拿 OWASP 清单逐条走查，作为评审者的抓手

## 考察问题

既然提示注入没有可靠根治解，系统凭什么还能安全上线？（线索：把模型当不可信组件，安全边界放在工具权限与数据隔离层——类比浏览器与操作系统）

## 经验之谈

Simon Willison 长期跟踪提示注入，核心判断（观点转述）——间接提示注入是 LLM 应用最棘手的安全问题，且无法靠提示词根除；原文见其博客 tag 页（https://simonwillison.net/tags/prompt-injection/）。

## 架构师视角

- 解决什么问题：LLM 应用上线前的安全底线
- 何时用：任何接外部数据 / 带工具权限的 LLM 应用；何时不用：纯本地单轮问答可简化
- 权衡：安全措施（人在环节、隔离执行）与体验/成本之间的取舍
- **平台提供了什么能力边界**：隔离执行（独立容器 / ServiceAccount）、网络策略是平台能力；模型层风险需业务侧防御
- **业务接入点在哪**：工具权限设计、输出校验、高危动作确认流程
- **需要和基础设施团队对齐什么**：Agent 运行环境的隔离级别、ServiceAccount 与 RBAC 最小权限、审计日志

## 常见问题排查

| 现象 | 排查路径 |
|---|---|
| Agent 执行了未预期的操作 | 查工具权限与配额，回滚到只读白名单，高危动作加人在环节 |

| 系统提示被套出 | 查日志是否泄露 prompt 原文，评估系统提示泄露面 |
