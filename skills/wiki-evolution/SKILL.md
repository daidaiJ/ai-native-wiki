# wiki-evolution：AI 驱动的 IT 类 wiki 演进工作流（创作 + 学习双期）

> 从 ai-native-on-k8s 项目（2026-08）提炼。核心信念：**wiki 是长期演进的知识资产，AI 是内容生产流水线**——草稿与正式内容分离、产出物直接可合入、任务按文件边界切分、版本粒度等于内容单元；内容主体完成后，AI 从内容生产者转型为**学习教练**，引导学习者从核心技能到业务心法、框架理论、趋势前瞻逐层提升。

## 一、核心模式（为什么这样做）

1. **AI 是流水线不是评审工具**：多模型（glm/grok/kimi…）并行产出草稿，要求「直接可合入的内容增补」而非评审意见——评审是中间态，浪费一轮。草稿归档 `meta/`（暂存区），正式内容进 `docs/`（正式区），可追溯可复用。
2. **任务分解粒度 = 文件边界**：subagent 各写自己的文件集（按 Part/章节目录切分），零冲突、可并行、可独立验收。不按「任务类型」切分。
3. **内容资产化 + 细粒度版本管理**：每个章节单独 commit——历史可追溯、单章可回滚、评审可按章。commit 粒度 = 内容单元。
4. **规划文档是活文档**：PLAN（大纲）/ SPEC（规格与模板）/ REQUIREMENTS（需求基线）/ AGENTS（协作规约）四件套先行；内容增补必须同步大纲表与需求编号，否则大纲与内容漂移。
5. **元层沉淀**：工作流本身也要被沉淀成 skill——不仅学内容，还学「如何用 AI 高效生产内容」，可迁移到其他 IT 类 wiki 项目。

## 二、项目骨架

```
<wiki 项目>/
├── PLAN.md          # 大纲规划：Part 章节表 + 业务痛点 + 演进叙事
├── SPEC.md          # 规格：章节模板、目录组织、质量标准
├── REQUIREMENTS.md  # 需求基线：R 编号表 + 追溯表 + 变更记录
├── AGENTS.md        # AI 协作规约：来源标注/验证环境/经验之谈纪律
├── docs/            # 正式内容，按 Part 组织
│   ├── part1-xxx/   #   每 Part：README.md（章概览）+ NN-章节.md
│   └── appendix/    #   知识检索手册（来源权威，全项目唯一链接库）
├── meta/            # AI 草稿归档（glm/grok/kimi…，合入后保留原文）
└── examples/ labs/  # 可运行示例与阶段项目
```

**知识检索手册**（`docs/appendix/knowledge-retrieval-guide.md`）是第三层一致性来源：所有正文链接统一维护在手册（按主题域分节），正文不重复堆链接；「经验之谈」人物只从手册已收录来源选取（防编造）。

## 三、工作流（五阶段）

### 阶段 0：规划先行（一次性）
PLAN/SPEC/REQUIREMENTS/AGENTS 四件套 + 检索手册就位。新增主题先查检索手册定位权威来源，再动笔。

### 阶段 1：多模型调研 → meta/ 草稿
- 派多个模型（或多次会话）对同一主题产出增补草稿，归档 `meta/<模型名>.md`
- **prompt 要求「直接可合入」**：按项目章节模板写实际增补内容，不是评审意见；命令统一标「验证环境：待验证」；拿不准的引用标 ⏳ 或「观点转述 + 待补引用」，禁止编造人名
- 多模型产出交叉互补（如 A 补内容、B 补来源、C 补规范），合入时择优整合

### 阶段 2：草稿合入（核心）
1. **同步大纲**：新章节编号先落 PLAN §3 大纲表（如 1.9/2.7/3.5），REQUIREMENTS 增补需求编号（R27-R37 模式），检索手册增补来源表——三层同步先行
2. **拆 subagent 并行写作**：按 Part/文件边界拆分，每个 agent 只写自己的文件集（见第四节 prompt 模板）
3. **合入纪律**：以草稿为骨架按章节模板补全，不另起炉灶；增强/前置小节命名 `NNa-主题.md` 并在 README 导航表标注「X.X 增强」；未写章节在导航表标「规划中」

### 阶段 3：版本管理
- 初始化：`git init -b main` + `.gitignore`（排除 AI 工具目录 `.qwen/ .codebuddy/ .workbuddy/ graphify-out/`）+ 首次 commit（规划文档）+ `git remote add origin <url>`
- **每章节单独 commit**：`docs(partN): 章 README 概览层` / `docs(partN): X.X 主题`——README 单独一个，每个详解文件一个
- 提交前验证：文件结构符合模板（grep 标题层级）、「验证环境：待验证」标注齐全、`git status` 无越界修改

### 阶段 4：元层沉淀
工作流跑通后提炼成 skill（本文件）：核心模式 + 骨架 + 工作流 + 模板 + 扩展路径。新项目直接复用。

## 四、subagent 拆分规范（渐进式披露）

**prompt 只给「任务文件路径 + 关键约束 + 验收标准」**，让 agent 自己 read_file 加载细节（草稿、SPEC 模板、AGENTS 纪律），不要把任务全文复制进 prompt——避免上下文膨胀，也让 agent 按需读取。

```text
你在 <仓库> 工作。任务：把 meta/<草稿>.md 第 X 节合入 docs/partN-xxx/，创建：
1. docs/partN-xxx/README.md（章 README 概览层）
2. docs/partN-xxx/NN-主题.md（X.X 章节）
【必读】meta/<草稿>.md 第 X 节（素材骨架）、SPEC.md §4/§5（模板）、AGENTS.md（纪律）、
        PLAN.md 对应 Part、docs/appendix/knowledge-retrieval-guide.md §N/§10（来源与人物表）
【约束】只创建上述文件，禁止写其他章节、禁止修改 PLAN/SPEC/REQUIREMENTS/meta/检索手册；
        以草稿为骨架按模板补全；命令标「验证环境：待验证」；经验之谈只引手册已收录人物，
        拿不准只写观点不署名；链接保持草稿原样，⏳ 保留，不联网验证
【验收】文件存在且符合模板、README 导航表覆盖详解文件、无编造引用
这是纯文档写作任务，禁止额外实验/联网搜索。写完即报告。
```

要点：并行 agent 写不同目录（无冲突）；主 agent 定期检查进度，发现跑偏立即 send_message 纠正；agent 完成后主 agent 统一验证 + 逐章节 commit。

## 五、章节模板三件套（可迁移的格式契约）

| 层 | 内容 | 约束 |
|---|---|---|
| 章 README（概览层） | 一句话说明 + 快速导航表 + 核心特性块（3~6 条 ✅）+ 前置知识表 + Mermaid 学习路线图 + 业务场景映射表 | < 50 行 |
| 正文（详解层） | 概念（业务痛点驱动 + 从哪来/是什么/往哪去）→ 动手（可复现）→ 实用技巧 → CKAD 考点对照（Part 1 才有）→ 考察问题（给线索不给答案）→ 经验之谈（真实来源）→ 架构师视角（固定三问：平台能力边界/业务接入点/与基础设施团队对齐项） | 每篇一个主题，cookbook 风格 |
| 章尾（收束层） | 核心收获表（验收标准）+ 推荐开源项目表（链接指向检索手册）+ 常见问题排查 | 高频报错 → 排查路径 |

## 六、扩展路径（新主题域接入）

1. 查检索手册定位权威来源（官方文档优先，标注深度 L1/L2/L3）
2. PLAN 大纲表加章节编号 + REQUIREMENTS 加需求编号 + 检索手册加来源表（三层同步）
3. 按第四节规范派 subagent 写作（或先多模型调研出草稿再合入）
4. 每章节单独 commit；README 导航表同步更新
5. 新主题跑通后，把可复用的部分回填本 skill

## 七、纪律清单（防翻车）

- 事实第一：数据/引用标注来源 + 日期，拿不准标「待验证」/⏳，禁止编造人名出处
- 命令必须本地集群验证后发布，未验证一律标「验证环境：待验证」
- 经验之谈只从检索手册已收录人物选取；「具体引用待补」就保持观点不署名
- 术语首现给一句话解释；纯中文；[实用]/[进阶] 双轨标注
- 合入后 meta/ 草稿原文保留（归档不删）；git 提交前检查无越界修改

## 八、学习期：AI 辅助学习工作流（内容主体完成后）

wiki 内容主体完成后，项目从「创作期」转型「学习期」——AI 的角色从内容生产者变为**学习教练**。转型与持续学习流程：

### 8.1 创作期 → 学习期转型（一次性）

1. **归档创作文档**：`git mv PLAN.md SPEC.md REQUIREMENTS.md AGENTS.md meta/archive/`（保留历史，只读引用）
2. **制定学习版文档**（根目录原位替换）：
   - `AGENTS.md`（学习版）：AI 四角色 + 使用纪律三条 + 四层提升引导 + 每章学习姿势
   - `SPEC.md`（学习版）：四层目标模型 + 章节结构 + 节奏自测 + AI 学习法
   - `LEARNING.md`：三阶段路径 + 四层提升落点 + 阶段验收 + 持续学习机制
3. **总引导入口**：根 `README.md`——快速开始 + 学习导航 + 内容目录 + AI 学习说明 + 项目状态（含归档位置）
4. **各级 README 更新**：每个 Part README 加一行「💡 用 AI 学本章」指引（考察问题当讨论伙伴/报错让 AI 解释/练习变体检验），指向根 README
5. **补全 skill**：本文件追加学习期工作流（即本节）

### 8.2 AI 学习教练四角色（辅助学习时按需切换）

| 角色 | 职责 | 用法 |
|---|---|---|
| 陪练 | 出题/批改/追问 | 考察问题当讨论伙伴，苏格拉底式追问，给线索不给答案 |
| 老师 | 概念类比/术语人话 | 术语首现一句话解释，先人话后术语，追问到懂 |
| 评审 | 找漏洞 | 对照「架构师视角固定三问」评审 YAML/方案/代码 |
| 检索加速器 | 定位权威来源 | 先查检索手册，再定位官方文档/KEP/论文 |

**使用纪律三条**：AI 会编造（事实回官方验证）；AI 不是验证环境（命令本地跑通）；AI 不替代思考（先自己想）。

### 8.3 四层提升引导（学习教练的核心职责）

| 层 | 方向 | 引导方式 |
|---|---|---|
| L1 | 核心技能（会用） | 动手章节跑通、lab 交付、kubectl 技巧熟练 |
| L2 | 业务心法（会选会对齐） | 固定三问：平台能力边界？业务接入点？与基础设施团队对齐什么？ |
| L3 | 框架设计理论（架构认知） | Part 4/6：模式、ADR、SLO、案例研读「问题→约束→决策→教训」 |
| L4 | 趋势前瞻 | 演进叙事（推理网关/Inference Extension/llm-d/KAITO 等），引导判断「下一步学什么」 |

### 8.4 每章学习姿势（高频）

- 学完一章：让学习者自述「核心收获表」，AI 追问补漏
- 考察问题：先让学习者答，再追问，最后才给线索
- 动手报错：先让学习者 `kubectl describe/logs` 自排，AI 解释 + 给排查路径
- 练习变体：改参数/改场景重做，检验是否真懂
- 阶段验收：按 LEARNING.md 验收标准出综合题

### 8.5 持续学习机制

- 每季度：案例研读 1 篇（固定信源：ACM Queue / Latent Space / InfoQ）+ 检索手册来源刷新
- 每阶段：四层模型自评（L1-L4 各到哪层），调整下一阶段精力分配
- 持续：追踪演进主线新秀，判断对业务的影响
