# 从云原生到 AI 云原生：开发者转型学习手册 — 大纲规划

> 定位：引导传统功能开发者，从「实现功能」转向「设计系统」，成长为 AI 时代有架构视野和方案设计能力的资深开发 / 架构师。

---

## 一、项目定位

### 1.1 一句话定位
用最短路径让传统功能开发者掌握云原生 + AI 的**实用技术**（能上手干活），并提供**进阶支线**（有空闲和资源时）建立架构视野与方案设计能力。

**元 wiki 定位**：本项目同时是「学习手册」与「元 wiki」——内容层教领域知识（docs/ 各 Part），元层教「用 AI 学习」（Part 0.5）并沉淀「AI 辅助内容生产」工作流（AI 生成草稿归档于 `meta/`，整合后进入 docs/ 与规划文档）。一句话：**不教 AI coding，教「用 AI 学习」；不只产出内容，也把 AI 辅助学习与生产的方法沉淀进 wiki。**

### 1.2 目标读者画像
- **业务开发 / 中台开发**：负责业务系统、业务中台/技术中台服务，日常以「写业务代码、调接口、CRUD」为主
- **基础设施二开适配者**：不建设基础设施，但对基础设施做二次开发、适配、集成（对接公司 PaaS/云平台、基于 K8s API 做定制、适配内部平台能力）
- 对 K8s 只有概念性了解，未系统学习过
- 对 LLM 应用停留在「调 API」层面，未做过完整 AI 系统
- 职业目标：资深开发 / 架构师（业务/中台视角），能独立完成技术方案设计
- **明确排除**：基础设施建设者（SRE / 平台工程师 / 集群管理员）——本手册教「驾驭平台、适配平台」，不教「建设平台」

### 1.3 设计原则
| 原则 | 说明 |
|---|---|
| **双轨制** | 主线 = 快速掌握实用技术（必学）；支线 = 架构认知与设计思维（进阶，按需） |
| **项目驱动** | 每个阶段一个可交付的小项目，学完即用、即验证 |
| **CKAD 锚定** | 基础篇对齐 CKAD 考点，学习有标准、练习有目标 |
| **来源权威** | 官方文档优先，大牛博客补充，每篇标注来源 |
| **演进视角** | 不只讲「是什么」，还讲「从哪来、为什么、往哪去」——这是架构思维的训练 |
| **考察引导** | 每章设提高向考察问题，引导学习者主动探索，而非单向灌输 |
| **经验传承** | 引用行业资深工程师/技术先锋的观点与总结，让学习者站在前人肩膀上 |
| **事实第一** | 所有事实与数据可验证（来源 + 日期），禁止编造；拿不准就标注「待验证」 |
| **通俗语言** | 术语首次出现即给一句话解释，先讲人话再讲术语，降低认知难度 |
| **cookbook 风格** | 短篇、步骤式、清单式，命令可直接复制运行，每篇解决一个具体问题 |
| **深度分级** | 内容标注 L1 会用 / L2 会选会对齐 / L3 会建——L3（建设平台）不展开，正文最多写「找基础设施团队」 |
| **AI 辅助学习** | 教学习者把 AI 当学习教练（答疑/出题/评审/检索加速），**不教「用 AI 写代码」**——AI coding 是另一门课，本手册只教「用 AI 学习」（Part 0.5） |
| **业务驱动** | 每章关联企业/消费者真实业务痛点与场景实例（标注 [已必备] = 当下刚需 / [潜在] = 近未来 1~3 年），引导学习者反思业务的长期发展与设计演进——技术选型服务于业务价值 |

### 1.4 与传统教程的差异
- 不追求 K8s 全量知识，只覆盖「开发者必须会」的部分（CKAD 范围即边界）
- 每章都有「架构师视角」小节：这个技术解决什么问题、何时用、何时不用、权衡是什么
- 强调「心智模型转换」：从单体思维 → 云原生思维 → AI 原生思维
- 纯中文文档形态：无视频、无图片/直播内容，全部内容可检索、可引用
- **平台使用者定位**：教「驾驭平台、适配平台、与基础设施团队协作」，不教「建设平台」；基础设施深度内容只讲能力边界与业务接入
- **不教 AI coding**：本手册教「用 AI 学习」——把 AI 当学习教练，加速掌握云原生 + AI 领域知识（详见 0.5）；不教「用 AI 写业务代码」

## 二、学习路径设计（核心）

### 2.1 三阶段总览

```
阶段一「能干活」  云原生基础 + 部署实战       约 4~6 周   → 能把应用容器化并部署到 K8s
阶段二「会做 AI」  LLM 应用 + Agent + 上云     约 4~6 周   → 能设计并交付一个 AI 应用
阶段三「懂架构」  架构模式 + 方案设计 + 前沿   持续学习   → 能独立完成技术方案设计
```

### 2.2 阶段一：云原生基础（实用主线，CKAD 全覆盖）
- **目标**：掌握容器化 + K8s 核心操作，达到 CKAD 应试水平
- **章节**：Part 1（9 章，见下）
- **阶段项目**：把一个传统 Web 应用（如 Spring Boot / FastAPI）容器化，部署到 K8s，完成配置管理、探针、滚动更新、Ingress 暴露
- **验收标准**：能独立完成 CKAD 模拟题 60%+；能解释自己部署的每个资源对象

### 2.3 阶段二：LLM 应用与上云（实用主线）
- **目标**：掌握 LLM 应用架构模式（RAG/Agent），并能部署到 K8s
- **章节**：Part 2 + Part 3
- **阶段项目**：RAG 问答应用 + 一个工具调用 Agent，完整上云（推理服务 + 弹性 + 监控）
- **验收标准**：能独立设计一个 AI 功能的技术方案（选型 + 架构 + 部署）

### 2.4 阶段三：架构进阶（进阶支线，按需学习）
- **目标**：建立架构视野，掌握方案设计方法论
- **章节**：Part 4 + Part 5 + Part 6
- **建议节奏**：每周 1~2 章，配合案例研读
- **验收标准**：能输出一份完整的架构设计方案文档（需求 → 选型 → 架构 → 风险）

### 2.5 时间投入建议
| 场景 | 建议 |
|---|---|
| 每天 1 小时 | 阶段一约 8 周，阶段二约 8 周 |
| 每天 2~3 小时 | 阶段一约 4 周，阶段二约 4 周 |
| 周末集中 | 阶段一 2 个周末 + 阶段二 2 个周末 |

## 三、章节大纲

> 标注说明：**[实用]** = 主线必学；**[进阶]** = 支线按需；**[CKAD]** = 对应 CKAD 考点

### Part 0 转型导论（0.5 周）
- 0.1 为什么是现在：AI 时代开发者能力地图（功能开发 → 系统设计 → 架构决策）
- 0.2 学习路径与时间规划（本文档第二章）
- 0.3 环境准备：Docker + kind + kubectl，30 分钟搭好本地集群
- 0.4 心智模型转换：单体思维 vs 云原生思维 vs AI 原生思维
- 0.5 用 AI 学习：把 AI 变成你的学习教练 [实用]
  - 定位红线：本手册教「用 AI 学习」，**不教「用 AI 写代码」**（AI coding 是另一门课）；AI 是学习加速器，不是学习替代品——手册教的技能必须自己会
  - AI 的四个学习角色：**陪练**（出题/批改/追问）、**老师**（概念类比/术语人话/追问到懂）、**评审**（YAML/方案找漏洞）、**检索加速器**（定位官方文档/KEP/论文，配合知识检索手册）
  - 使用纪律三条：AI 会编造——事实/版本/数据必须回官方文档验证；AI 不是验证环境——命令必须本地 kind 跑通；AI 不替代思考——考察问题先自己想，再让 AI 苏格拉底式追问
  - 用 AI 学本手册的具体姿势：把知识检索指南喂给 AI 助手按主题域查源；每章「考察问题」用 AI 当讨论伙伴；lab 报错让 AI 解释 + 给排查路径（以 kubectl describe/logs 为准）；让 AI 生成练习变体（改参数/改场景）检验是否真懂
  - 经验之谈：AI 时代的学习能力 = 提问能力 + 验证能力（观点，待补引用）

**业务痛点与场景实例**
- [已必备] 企业 AI 转型焦虑：业务方拿着 ChatGPT 演示要求「我们也做一个」，开发团队不知从何接起；传统 IT 团队被要求降本增效，技术栈老化、招人难
- [已必备] 消费者对「即时、个性化、智能」体验的期望已成默认（智能客服、个性化推荐），做不到就流失
- 场景实例：企业 AI 试点多、落地少——「有 AI 演示」与「有业务价值」之间的鸿沟
- 引导反思：开发者的价值从「实现功能」转向「设计系统」——把业务问题翻译成技术方案的能力，是 AI 时代最稀缺的

**业务痛点与场景实例**
- [已必备] 客服人力成本高、企业知识检索难（文档散落、专家经验随人流失）、内容生产人力瓶颈

- 场景实例：企业知识库 RAG 问答（把散落文档变成 7×24 问答）、智能客服降本、Agent 自动化工单流转、营销内容批量生成
- 引导反思：AI 应用的价值 = 业务指标改善（成本/效率/体验），不是「有 AI 就行」——评估先行（2.5），没有评估集的 AI 项目不允许上线

### Part 3 AI 应用上云（阶段二，约 2 周）[实用]
> 视角：业务团队如何使用 AI 基础设施（申请 GPU、部署推理、接入服务），不建设 GPU 平台

- 3.1 把 LLM 应用部署到 K8s：部署模式、弹性伸缩、事件驱动
- 3.2 模型推理服务：vLLM / SGLang / KServe / BentoML，OpenAI 兼容 API
- 3.3 GPU 资源管理：Device Plugin / GPU Operator / Kueue 调度（业务视角：怎么申请、怎么排队）
- 3.4 AI 应用可观测与成本：GPU 监控（dcgm-exporter 接入 Prometheus）、Token 成本、推理缓存 + 成本分摊（showback：利用率 × 卡单价 → 按 namespace 出「AI 账单」）
- 3.5 LLM 网关与成本治理 [实用]：LiteLLM / Envoy AI Gateway、虚拟 key 与月度预算、provider fallback、OTel GenAI 打点、按团队/feature 维度 showback

**业务痛点与场景实例**
- [已必备] GPU 贵且缺（排队等卡）、推理延迟毁体验、token 成本失控（月底账单吓人）、被单一模型厂商绑定（涨价/断供被动）
- [潜在] 多模型并存成为常态：不同业务用不同模型（成本/合规/效果），统一管控成为刚需
- 场景实例：AI 应用上线后 QPS 上不去（弹性没做好）、GPU 利用率低但账单高、大模型 API 涨价被迫切换供应商
- 引导反思：AI 应用的成本结构（GPU/token）决定商业模式是否成立——网关、可观测、成本分摊是规模化前提，不是锦上添花

### Part 4 云原生架构进阶（阶段三）[进阶]（业务/中台 + 二开适配视角）
- 4.1 云原生设计模式：12-Factor、Kubernetes Patterns（Sidecar/Ambassador/Adapter 等）——业务应用怎么设计
- 4.2 可观测性接入：业务应用如何接入 OTel / Prometheus / Grafana（埋点、指标、日志、追踪），从指标到 SLO
- 4.3 GitOps 交付：业务团队如何使用 ArgoCD / Flux 声明式交付应用
- 4.4 平台能力边界：服务网格（Istio 流量管理对业务的价值）/ 网关 / eBPF 网络——了解能力、业务接入适配，不深入实现
- 4.5 平台工程使用者视角：IDP 黄金路径、自助服务，如何在平台上高效交付
- 4.6 K8s 二开适配基础：K8s API 编程（client-go）、CRD 理解与使用、Operator 模式理解（为什么有 Operator、怎么用）、平台能力集成（配置中心/网关/可观测对接）
  - 写作主线：Kubebuilder book 先跑通一个 CRD + Controller，再回看 client-go 原理（避免陷入源码细节）
  - client-go 三套姿势：一次性 List/Get（低频同步）→ Watch + Informer（二开标配）→ Dynamic client（处理任意 CRD）
  - 工程坑：reconcile 禁止长阻塞（外部调用放 workqueue 异步）；controller 独立 ServiceAccount 配最小 RBAC；Lister 读本地缓存（最终一致）
  - 判断力：很多「想写 Operator」的场景一个 CronJob 就够——Operator 的价值在「状态驱动的自愈」
- 4.7 架构决策方法：选型框架、权衡分析、演进式架构

**业务痛点与场景实例**
- [已必备] 系统耦合改不动（改一行牵一发动全身）、发布风险高（上线即事故）、故障爆炸半径大（一个服务挂了拖垮全站）、平台能力重复建设（每个团队各造一套轮子）
- [已必备] 业务增速放缓后，降本增效成为硬指标——资源利用率、交付效率被摆上台面
- 场景实例：单体应用拆不动、灰度发布救了一次大事故、IDP 黄金路径解决「开发等平台」的排队问题
- 引导反思：架构演进是业务规模与组织复杂度逼出来的，不是技术时髦——先有业务约束，后有架构决策（ADR 记录「为什么」）

- 5.5 前沿方向：WASM、边缘 AI、Serverless 推理、推理时缩放

**业务痛点与场景实例**
- [潜在→已必备] 多模型并存管理难（成本/合规/容灾三线作战）、AI 系统可靠性（幻觉/故障/降级）、Agent 安全（越权/提示注入）、AI 成本治理（GPU 与 token 双账单）
- [潜在] 消费者侧：AI 功能成为产品标配（智能助手/自动摘要/个性化生成），没有 AI 能力的产品在竞争中掉队
- 场景实例：企业同时接多家大模型做容灾与比价、Agent 越权操作造成业务事故、AI 账单失控被 CFO 问责
- 引导反思：AI 系统设计 = 可靠性 + 成本 + 安全的三重约束；AI 原生架构（推理网关/调度/可观测）是下一波业务竞争力的基础设施

### Part 6 架构师修炼（阶段三，持续）[进阶]
- 6.1 方案设计方法论：需求分析 → 技术选型 → 架构设计 → 方案文档模板（内嵌 3~5 篇 ADR——一页纸记录一个决策的「为什么」，比长篇论证更可维护；模板见 meta/glm.md 草稿）
- 6.2 系统可靠性设计：SLO / 容灾 / 容量规划 / 故障演练（SLO 起步三步：先挑 1 个用户可感知的 SLI → 定一个「敢公布」的 SLO → 每月复盘错误预算消耗；预算烧完冻结新功能发布）
- 6.3 案例研读：知名系统架构解析（每季度更新；固定信源：ACM Queue / Latent Space / InfoQ，每季度各挑 1 篇做「问题 → 约束 → 决策 → 教训」拆解）
- 6.4 持续学习：大牛博客 / 官方文档 / 论文 / 社区路线

**业务痛点与场景实例**
- [已必备] 技术决策失误代价高（一次错误选型 = 两年重构）、系统不可靠导致事故与信任崩塌、架构师断层（能设计系统的人稀缺）
- [潜在] 业务不确定性加剧：市场变化快，架构要能「边打边改」——演进式架构、快速试错成为生存能力
- 场景实例：一次错误选型导致的重构复盘、SLO 事故复盘（错误预算烧完冻结发布）、方案评审在立项前拦住一个坑
- 引导反思：方案设计能力 = 业务理解 + 技术权衡 + 长期演进视角——架构师的价值在「决策质量」，不在「代码量」

## 五、核心叙事线：云原生 → AI 云原生的演进（调研结论，2026-08）

> 这是贯穿全书的「架构思维主线」：每个主题都在这条线上定位。

### 5.1 演进三阶段
1. **云原生成熟期（2022-2024）**：K8s 稳定迭代（每年 3 版本），周边生态毕业潮（Cilium/ArgoCD/Knative/Backstage），平台工程取代「人人自建工具链」
2. **AI 就绪期（2024-2025）**：K8s 原生长出 AI 桥梁能力——DRA（GPU 统一资源模型，1.35 GA）、Gateway API Inference Extension（模型路由）、Workload-Aware Scheduling、In-Place Pod Resize
3. **AI 云原生期（2025-2026）**：CNCF 主题全面转向「AI factory」「LLMOps 平台工程」；推理引擎（vLLM 90k star）与 Agent 协议（MCP/A2A）标准化；Kagent 等「Agent 原生」项目进入 CNCF

**AI 桥梁四层结构**（Part 3/5 的展开骨架）：
- 调度层：DRA + Kueue/Volcano（GPU 资源怎么管）
- 流量层：Gateway API Inference Extension（模型路由怎么走）
- 运维层：K8sGPT / GPU 预测性扩缩容（AI 负载怎么运维）
- 可观测层：OpenTelemetry GenAI 语义约定（AI 调用怎么观测）

### 5.2 各 Part 核心项目演进速查

**Part 1 云原生基础**（CKAD 锚定，无项目演进负担）
- 版本特性：Gateway API 取代 Ingress、Native Sidecar、In-Place Pod Resize、Metrics API GA

**Part 2 LLM 应用开发**（框架演进史是重点）
- 演进线：LangChain 链式（2022）→ LangGraph 图状态机（2024）→ LangChain 1.0 统一（2025-10）→ Deep Agents（2026）
- 已过气：Swarm（→Agents SDK）、AutoGen 0.2（→Agent Framework）、LangChain 0.x
- 2026 值得学：LangGraph、Dify、OpenAI Agents SDK、MCP/A2A、Langfuse、GraphRAG 系

**Part 3 AI 应用上云**
- 推理：vLLM（事实标准，PagedAttention/连续批处理/OpenAI 兼容 API）→ SGLang 挑战者 → KServe 平台层
- GPU：Device Plugin → DRA（1.35 GA）；Kueue（排队/配额标准）→ Volcano（Gang 调度）
- 部署模式：vLLM+Operator、KEDA 事件驱动、Knative scale-to-zero、Envoy AI Gateway 统一网关

**Part 4 云原生架构进阶**
- 设计范式：12-Factor → Kubernetes Patterns → 平台工程（IDP/Backstage）
- 可观测：Prometheus → OpenTelemetry 标准 + Grafana LGTM
- 网络：Ingress → Gateway API；服务网格 sidecar → Ambient（sidecar-less）

**Part 5 AI 架构进阶**
- K8s×Agent 三线：AI 运维 K8s（K8sGPT/kubectl-ai）→ Agent 原生上 K8s（Kagent CRD+MCP）→ AI 应用部署模式栈
- 训练：TorchX 归档 → KubeRay + TorchElastic + JobSet 收敛
- 前沿：disaggregated inference（预填充/解码分离）、NVIDIA Dynamo、ModelPack（OCI 化模型分发）

### 5.3 学习性价比标注（云原生工程师进入 AI 领域）
- **第一梯队（直接复用 K8s 知识，先学）**：K8s GPU/DRA 官方文档 → Kueue → vLLM → KServe
- **第二梯队（按需深入）**：Ray/KubeRay → JobSet+TorchElastic → HAMi → MLflow
- **第三梯队（特定场景）**：Volcano → Kubeflow → SGLang/TGI → Ollama → BentoML
