# SPEC — 从云原生到 AI 云原生：开发者转型学习手册

> 版本：v0.1（草案） · 状态：规划中

## 1. 项目定义

| 项 | 内容 |
|---|---|
| 项目名 | ai-native-on-k8s（从云原生到 AI 云原生） |
| 形态 | 开源知识 wiki + 学习手册（文档为主，含可运行示例）；**元 wiki**——内容层教领域知识，元层教「用 AI 学习」（Part 0.5）并沉淀 AI 辅助内容生产工作流（草稿归档 `meta/`） |
| 愿景 | 让传统功能开发者以最短路径掌握云原生 + AI 实用技术，并进阶建立架构视野与方案设计能力 |
| 目标读者 | 业务开发/中台开发 + 基础设施二开适配者（**不建设平台**，使用/适配/集成平台），目标角色：资深开发 / 架构师（业务/中台视角） |
| 定位红线 | 不教「用 AI 写代码」（AI coding）；教「用 AI 学习」——学习者如何借助 AI 加速掌握手册内容（Part 0.5） |
| 语言 | 纯中文（不做 i18n） |
| 内容形态 | 纯文档（无视频、无图片/直播内容），全部内容可检索、可引用 |

## 2. 核心设计决策

1. **双轨制内容**：主线（实用技术，必学，快速见效）+ 支线（架构认知，进阶，按需）
2. **CKAD 锚定**：基础篇对齐 CKAD 考点，作为学习标准与练习目标
3. **项目驱动**：每阶段一个可交付项目，学完即用
4. **演进视角**：每个主题讲「从哪来 → 是什么 → 往哪去」，训练架构思维
5. **来源权威**：官方文档优先，大牛博客补充，全部标注来源
6. **实操验证**：所有命令与 YAML 本地集群验证后发布
7. **考察引导**：每章设提高向考察问题，引导学习者主动探索（给线索不给答案）
8. **经验传承**：引用行业资深工程师/技术先锋的观点与总结，标注出处
9. **事实第一**：所有事实与数据可验证（来源 + 日期），禁止编造；拿不准标注「待验证」
10. **通俗语言**：术语首次出现即解释，先人话后术语，降低认知难度
11. **cookbook 风格**：短篇、步骤式、清单式，命令可复制，每篇解决一个具体问题
12. **深度分级**：内容标注 L1 会用 / L2 会选会对齐 / L3 会建——L3（建设平台）本项目不展开，正文最多写「找基础设施团队」
13. **AI 辅助学习**：教学习者把 AI 当学习教练（Part 0.5），不教 AI coding
14. **业务驱动**：每章关联企业/消费者真实业务痛点与场景实例（标注 [已必备] = 当下刚需 / [潜在] = 近未来 1~3 年），引导学习者反思业务的长期发展与设计演进——技术选型服务于业务价值

## 4. 章节模板（统一格式）

> 结构参考 ai-infra 学习项目（D:\note\AIIfra\ai infra）的三层文档体系，适配纯文档 wiki 定位：**章 README（概览层）→ 正文（详解层）→ 章尾（收束层）**。

### 4.1 章 README（概览层，< 50 行）

每章入口页（如 `docs/part1-cloud-native/README.md`），让学习者与 agent 一眼定位：

1. **一句话说明**：本章解决什么问题
2. **快速导航表**：章内文档/示例 → 说明（标注 📖 详解 / 🔧 示例 / 📋 总结）
3. **核心特性块**：✅ 学完能做什么（3~6 条）
4. **前置知识表**：知识点 → 来源章节 → 在本章的应用（形成章节依赖链）
5. **学习路线图**：Mermaid 图展示本章学习阶段划分
6. **业务场景映射表**：业务痛点/场景 → 本章技术方案（呼应「业务驱动」原则，标注 [已必备]/[潜在]）

### 4.2 正文（详解层，每篇一个主题，cookbook 风格）

每篇固定结构：
1. 概念：为什么需要（**业务痛点驱动**：关联企业/消费者真实痛点与场景实例，标注 [已必备]/[潜在]，引导反思业务长期发展与设计演进）
2. 动手：YAML + 命令，可复现
3. 实用技巧：日常高频操作
4. CKAD 考点对照（Part 1 章节）
5. 考察问题：提高向思考题，引导探索（附线索/参考来源，不直接给答案）
6. 经验之谈：行业资深工程师/技术先锋的观点与总结（引用原文 + 出处）
7. 架构师视角：解决什么问题 / 何时用 / 何时不用 / 权衡 + **固定三问**：平台提供了什么能力边界？业务接入点在哪（API / CRD / 控制台）？需要和基础设施团队对齐什么？——把「驾驭平台」的定位落到每一章的固定结构里

### 4.3 章尾（收束层）

8. **核心收获表**：能力维度 → 具体收获（即本章验收标准，呼应 PLAN 各阶段验收）
9. **推荐开源项目表**：项目 → 链接 → 研读重点（来源见知识检索手册，不重复堆链接）
10. **常见问题排查**（Troubleshooting）：高频报错 → 排查路径（如 Pod 被 PSA 拒绝、探针失败、chart 渲染报错）

## 7. 质量标准

- 每篇内容：来源标注（官方文档 / 博客作者）+ 验证环境说明
- 每个示例：可一键运行（提供脚本），CI 中做 YAML 语法校验
- 每章结尾：自测题（选择题 + 实操题）+ 考察问题（提高向，引导探索）
- 经验之谈：必须引用真实来源（作者 + 文章/演讲出处），禁止编造
- 事实纪律：数据/事实标注来源与日期；链接可访问；拿不准标注「待验证」
- 认知降载：术语首次出现给一句话解释；单篇聚焦一个主题，控制篇幅
- 学习路径：每阶段有明确验收标准（见 PLAN.md 第二章）
- 深度分级：每条内容标注 L1/L2/L3（见 §2 决策 12），L3 内容不展开
- 业务场景：每章至少 1 个真实业务场景实例（企业/消费者侧，标注 [已必备]/[潜在]）；痛点数据须有来源（行业报告/公开案例），禁止编造
- 章 README：每章必须有概览层入口（快速导航表 + 核心特性 + 前置知识 + 业务场景映射，< 50 行）
- Mermaid 图表：文本图表（符合纯文档定位，不违反「无图片」原则）；颜色语义——蓝 `#e3f2fd` 核心组件、绿 `#c8e6c9` 推荐方案/成功、橙 `#fff3e0` 重要步骤、红 `#ffcdd2` 问题/局限、粉 `#fce4ec` 元数据/配置
- 术语表（附录 C）以 K8s 官方中文文档译法为准，全书统一
- 「经验之谈」优先从知识检索手册 §10 已收录来源中选取（作者与出处固定可查，降低编造风险）
- AI 可观测内容统一以 OTel GenAI semconv 为字段标准（Part 3.4 / 4.2 / lab3 同一埋点口径，形成手册内部呼应）
- Part 4.6 以 Kubebuilder book 为写作主线：先脚手架跑通 CRD + Controller，再回看 client-go 原理
